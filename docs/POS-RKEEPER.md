# Подключение r_keeper

Серверный адаптер реализует чтение White Server API v2. Работа с реальной кассой ещё не подтверждена: ключи и доступ к ресторану не предоставлены. Локальные тесты используют ответы по опубликованному контракту API.

## Что нужно от заведения

- Действующая лицензия интеграции White Server и выданный токен агрегатора `AggregatorAuthentication`.
- `objectId` — код ресторана в системе лицензирования; White Server Agent не ниже 2.8.5.10.
- Разрешения `GetOrderList` для всех столов и закрытых заказов, доступ к `GetOrder`.
- Основная валюта ресторана RUB. В используемом ответе нет кода валюты; её нужно подтвердить при пилотной сверке. Суммы API трактуются как основные денежные единицы, переводятся в целые копейки без округления лишних десятичных знаков.
- Настроенное расширенное поле заказа, содержащее устойчивый идентификатор клиента. Имя этого поля задаётся в `customerIdProperty`. Владелец один раз связывает идентификатор с зарегистрированным гостем «Своих». Телефон, имя, `rkFriendsAnchor` и произвольный комментарий автоматически не сопоставляются.
- Настроенное расширенное поле с фактическим временем закрытия заказа, имя — `closedAtProperty`. Значение — ISO 8601 с часовым поясом, например `2026-11-10T14:30:00+03:00`. Это специальная настройка кассы/её интеграции: стандартные ответы не документируют время закрытия. Адаптер сам не создаёт и не заполняет поля на кассе.

Оформление лицензии и любые дополнительные платные услуги выполняются отдельно. Уже оплаченный VPS не предоставляет доступ к White Server. Порядок получения токена описан в [официальной документации API v2](https://docs.rkeeper.ru/ws/white-server-api-v2-27845668.html), разрешения — в разделе [«Рестораны»](https://docs.rkeeper.ru/ws/restorany-29419952.html).

## Проверка перед включением

Создайте в согласованном тестовом контуре или на пилоте один закрытый оплаченный заказ с заполненными полями клиента и времени закрытия. «Проверить соединение» запрашивает список и детали до восьми последних подходящих заказов. Пустой список либо отсутствие нужных полей не считается готовым подключением. Проверка не импортирует заказ и не начисляет бонусы.

Допускается только положительная сумма с точностью до копейки, `isFinished: true`, `unpaid: 0`, `isReturn: false`, `isReserve: false`. Сумма деталей должна совпадать со списком, остаток к оплате деталей — равняться нулю. Чек без подтверждённого времени закрытия поступает на сверку. Дата открытия, плановое время готовности и время получения ответа не подменяют дату закрытия.

## Обмен и ограничения

Адаптер отправляет только `GetOrderList`, `GetOrder`, `GetTaskResponse` на фиксированный HTTPS-адрес White Server. Получение ответа на задачу ограничено восемью проверками. Список по умолчанию ограничен 500 заказами; превышение лимита отклоняет весь пакет. Максимум четыре параллельных запроса деталей, 15 секунд на сетевой запрос, 120 секунд на загрузку пакета, 10 секунд на проверку готовности, 2 МиБ на ответ. Ошибки не выводят токен или необработанный ответ поставщика.

`GetOrderList` не документирует пагинацию, диапазон дат или полноту исторического архива. После длительного отключения полнота загрузки требует сверки с кассовым отчётом. `isReturn` не даёт документированной ссылки на исходный чек: возвраты не начисляют баллы и требуют сверки; автоматическое сторнирование без установленной связи не заявляется. Изменение уже загруженного чека также не должно повторно начислять бонусы.

Полные контракты: [список заказов](https://docs.rkeeper.ru/ws/getorderlist-119015281.html), [детали и расширенные свойства](https://docs.rkeeper.ru/ws/getorder-27846105.html), [получение результата задачи](https://docs.rkeeper.ru/ws/gettaskresponse-27846138.html).

## Локальная проверка

`node --test tests/server-rkeeper.test.mjs` проверяет авторизацию и адрес запроса, суммы, неполные/открытые/возвратные чеки, даты, привязку ответов к ресторану и задаче, ограниченные повторы, лимиты, ошибки и готовность пилотного чека. Эти проверки не заменяют проверку лицензии, реального кассового агента и контрольного начисления в заведении.
