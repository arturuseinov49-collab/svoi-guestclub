# Кассы iiko и r_keeper в «Своих»

Подготовлены серверные сетевые адаптеры iikoCloud и r_keeper White Server, очередь событий, импорт чеков и автоматическое начисление в бонусной системе «Своих». **Реальные заведения ещё не подключены: API-доступов нет.** Проверки используют отдельные тестовые базы и ответы по официальным схемам API. Работа с конкретной кассой подтверждается только после пилота.

## Несколько заведений

Руководитель открывает «Касса и “Свои”» в своём заведении. Для каждого подключения отдельно хранятся организация/ресторан, разрешённые кассы, клиентские привязки, состояние обмена и чеки. Одна внешняя организация не может одновременно начислять в два заведения. Руководитель управляет ключами и привязками; сотрудники видят журнал своего заведения; гостю эти данные не доступны.

API-ключи шифруются AES-256-GCM в SQLite. Ключ шифрования POS_MASTER_KEY хранится в окружении сервиса вне базы и архива приложения. Экран статуса не возвращает API-ключи. Руководитель отдельно может раскрыть свой токен вебхука iiko. Секреты формы живут только в памяти страницы и удаляются при её закрытии.

Подключения обрабатываются с параллельностью до 4. Это многопользовательский пилот на текущем VPS, не обещание промышленной нагрузки: бизнес-модель пока хранится одним JSON-снимком SQLite. Перед массовым запуском нужны нагрузочная проверка, нормализация таблиц и независимые резервные копии.

## Порядок подключения

1. Создать заведение, настроить программу бонусов, пригласить команду и гостей.
2. Получить разрешённый API-доступ у администратора кассы и поставщика интеграции. Их лицензии не входят в стоимость VPS.
3. Руководитель сохраняет настройки в приложении. Обмен остаётся выключенным; тестовые чеки песочницы в рабочую базу не попадут.
4. Настроить передачу кассового клиента и закрытия заказа, выполнить «Проверить». Проверка должна пройти не более чем за 15 минут до включения.
5. Включить обмен. Кассового клиента из полученного чека один раз связать с личным кодом уже вступившего в клуб гостя Telegram. Телефон и имя не используются для автоматического объединения людей.
6. Сверить оплаченный пробный чек, повтор события, неизвестного гостя, отключение связи и возврат с кассовым отчётом. До сверки не заявлять интеграцию проверенной на заведении.

## iikoCloud

Нужны appId/clientSecret приложения интеграции, apiKey заведения, organizationId, terminalGroupIds и смещение времени кассы от UTC. Локальная iiko без Cloud API этим адаптером не поддерживается.

Сервер использует авторизацию v2 и фиксированный HTTPS-хост api-ru.iiko.services. Проверяет организацию, RUB, принадлежность касс и часовой пояс. Руководитель получает адрес /api/pos/webhooks/iiko/<connectionId> и случайный секрет. Администратор iiko настраивает TableOrderUpdate с закрытыми/удалёнными заказами; предпочтительны все статусы. У организации один адрес вебхука: приложение его автоматически не меняет. Существующее подключение необходимо согласовать с администратором.

Приём проверяет секрет Authorization и организацию, сохраняет только ID заказа в долговечную очередь. Рабочий процесс повторно читает заказ через /api/1/order/by_id перед начислением. Нужны creationStatus=Success, status=Closed, положительная сумма, processedPaymentsSum >= sum, достоверное whenClosed, разрешённая касса. Отсутствие данных ведёт в ожидание или сверку. Гость — только customer.id, привязанный руководителем.

Поля по спецификации: by_id от 7.4.6, customer от 7.5.2, processedPaymentsSum от 7.6.0. API не даёт универсальной суммы/ссылки возврата. Deleted и изменения начисленного чека требуют сверки. Исторический импорт и гарантированное восстановление пропущенных самим поставщиком вебхуков не реализованы; сервер повторяет уже принятые события после сбоя.

Источники: [авторизация iiko](https://api.iiko.help/docs/concepts/authorization/), [вебхуки](https://api.iiko.help/docs/guides/webhooks/), [официальная OpenAPI-схема](https://api.iiko.help/docs/api-reference/).

## r_keeper White Server

Нужны лицензированная интеграция, токен AggregatorAuthentication, objectId, White Server Agent от 2.8.5.10 и разрешения читать все столы, закрытые заказы и детали GetOrder. Руководитель подтверждает расчёты в RUB: ответа с кодом валюты API не гарантирует.

Стандартный GetOrderList не даёт гарантированного ID гостя и времени фактического закрытия. Администратор должен обеспечить два extProperties: устойчивый ID клиента и фактическое время закрытия ISO 8601 с часовым поясом. Названия задаются при подключении. Время открытия/опроса и выдуманный гость не подставляются. Проверка требует закрытого пробного чека с этими полями.

Опрос примерно раз в минуту: GetOrderList с withClosed:true, GetOrder, ожидание заданий через GetTaskResponse. Сверяются ресторан, ID задания/заказа, суммы списка и деталей, isFinished, нулевые unpaid/sumToPay, отсутствие возврата/резерва. Ошибка части ответа не считается успешным полным опросом. По умолчанию максимум 500 чеков за ответ; превышение останавливает импорт без молчаливого усечения.

API не обещает полноту архива и связь возврата с исходным чеком. Возврат после начала подключения или с неизвестным временем останавливает это подключение до ручной сверки. Проверка ключей и пересохранение блокировку не снимают. Подробности и источники: [POS-RKEEPER.md](docs/POS-RKEEPER.md).

## Начисления и ограничения

Деньги проверяются в целых копейках, бонусы сервер рассчитывает по программе заведения. Чек, визит, начисление и запись обработки фиксируются одной транзакцией. Повтор провайдера/организации/ID не начисляет снова, включая перезапуск и потерю ответа. Чеки до начала подключения не начисляются. Чаевые и оценка не выдумываются.

Баланс ведётся в «Своих». Адаптеры не меняют бонусы iikoCard/r_k Loyalty, не закрывают заказы и не проводят оплату. Кассир выдаёт вознаграждение через интерфейс сотрудников.

Изменение начисленного чека блокирует дальнейшее автоматическое начисление этому гостю в заведении, в том числе через другую кассу. Автоматическое сторнирование, частичные возвраты, корректировка визитных порогов и интерфейс снятия блокировки после сверки пока не реализованы. Для снятия нужна отдельная сверка и согласованная корректировка журнала, а не удаление ошибки. Ручной визит и кассовой чек без общего ID не дедуплицируются: после подключения сотрудник не должен повторно отмечать тот же визит вручную.

Тестовая песочница остаётся отдельной: её данные живут в памяти и не вызывают рабочий API импорта.
